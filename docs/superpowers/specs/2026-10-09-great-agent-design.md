# GREAT Agent 第一版架构设计

- 日期：2026-10-09
- 状态：已完成对话评审，待用户审阅落盘版本
- 项目根目录：`F:\GREAT_Agent`
- 框架图：`docs/architecture/great-agent-architecture.svg`

## 1. 背景与目标

GREAT Agent 是面向 GNSS 卫星导航定位与大地测量科研的本地 Web Agent。完整科研链路为：

1. B2bOut PVTFLT 解算；
2. UPD 计算与归档；
3. PPPFLT 定位解算。

当前前两步已经完成。第一版只打通 PPPFLT 短链路，把上游产品视为只读输入。系统不重新实现数值解算算法，而是在现有 GREAT 程序、XML 模板、观测数据和产品文件之上提供自然语言计划、确定性校验、可恢复调度、日志管理和结果收集。

第一版首先服务单个开发者，运行于保存 D/F 盘科研数据和 GREAT 可执行程序的 Windows 电脑，只监听本机地址。架构保留未来在课题组服务器部署、增加账号权限和开源发布的接口。

## 2. 已确认的核心需求

### 2.1 用户入口

- 使用 React 网页进行对话、计划审核、任务监控和结果查看。
- 用户可以用自然语言创建或修改实验计划。
- 用户也可以直接编辑计划卡片。
- 两种修改方式统一产生版本化计划修订，不维护两套业务逻辑。

### 2.2 PPPFLT 实验语义

- 一个日任务对应一个年份与 DOY。
- 每个日任务的 XML 同时包含默认的 15 个测站，不把测站拆成 15 个独立任务。
- 日任务数量由用户实际输入的日期范围决定，不写死为 34。
- 当前典型场景为：2024 DOY 339–366 和 2025 DOY 001–006，共 34 个日任务。
- 日期段允许跨年、重叠和排除日期；后端负责合法性检查、拆分、去重和排序。
- 第一条真实冒烟实验为：2024 DOY 350、默认 15 站、Static、DF、Float、reset0。

### 2.3 第一版输出

- 冻结后的计划与 XML；
- 每个日任务的进程日志、退出码和状态；
- `.flt` 等 GREAT 输出文件清单；
- 整体实验汇总和失败原因。

时间序列图、参考坐标、N/E/U 或 XYZ 误差统计和收敛分析在取得第一份真实 `.flt` 后紧接着实现，不作为首个执行闭环的阻塞条件。

## 3. 范围与非目标

### 3.1 第一版范围

- 千问等 OpenAI 兼容模型 API；
- 自然语言到实验计划草稿；
- 卡片编辑与对话修改；
- 版本化计划、预检与冻结；
- 任意合法日期范围到 N 个可恢复日任务；
- PPPFLT XML 的确定性生成与标准 XML 校验；
- GREAT 子进程调度、停止、重试和恢复；
- 实时状态、日志和结果文件清单；
- 本机 SQLite 持久化；
- 模拟 GREAT 适配器与开源演示模式。

### 3.2 第一版非目标

- 自动运行 B2bOut PVTFLT；
- 自动计算或归档 UPD；
- 自动修改 GREAT C++ 解算内核；
- 多 Agent 协作或长期自主科研规划；
- 登录、课题组多人权限和远程公网访问；
- 完整数值质量评估和时间序列分析；
- Docker、Kubernetes、Redis、Celery 或微服务拆分。

## 4. 总体架构

采用 FastAPI + React + SQLite + 独立本地 Worker 的模块化单体架构。

### 4.1 React 前端

前端包含四个主要视图：

1. 对话与实验创建：输入自然语言，查看模型解释和缺失参数；
2. 计划审核：用卡片查看、编辑和比较计划修订；
3. 执行面板：查看总体进度、日任务状态、实时日志、停止和重试操作；
4. 结果页面：浏览日志、FLT 文件、任务清单和实验汇总。

前端不接触 API Key，不生成系统命令，也不能提交任意可执行文件路径或未验证 XML。

### 4.2 FastAPI 后端

后端负责：

- 调用 `ModelProvider`；
- 校验模型输出和前端编辑；
- 保存实验及计划修订；
- 执行输入预检；
- 冻结执行快照；
- 创建日任务；
- 提供任务、日志、事件和结果 API。

模型输出永远是候选数据，必须经过 Schema 和专业规则校验。执行开始后，模型不参与日期、路径、参数或命令决策。

### 4.3 独立本地 Worker

Worker 使用 SQLite 领取等待任务并执行 GREAT。它与 API 属于同一 Python 项目，但作为独立进程运行，避免长时间解算阻塞 Web 服务。

Worker 负责：

- 原子领取任务；
- 创建任务目录和 XML；
- 最后一次输入预检；
- 以参数列表启动 GREAT；
- 捕获 stdout、stderr、PID、退出码和时间；
- 识别必要输出；
- 更新状态并发布事件。

第一版不依赖 Redis 或外部消息队列。

### 4.4 适配器边界

- `ModelProvider`：统一 OpenAI 兼容模型接口，第一版使用千问；
- `GreatPppfltAdapter`：实验参数映射、输入规则、XML 生成、命令构造和结果识别；
- `TaskStore`：SQLite 中的实验、计划、任务、尝试和事件；
- `RunStorage`：`F:\GREAT_Agent\runs` 中的计划、XML、日志和结果；
- `ResultAnalyzer`：第一版只建立文件清单接口，后续扩展时间序列分析。

## 6. 实验计划模型

内部使用版本化 `ExperimentSpec`，前端使用卡片展示，不把 JSON 结构直接暴露成用户界面。

计划至少包含：

- Schema 版本、实验 ID、修订号和创建时间；
- 工作流类型 `pppflt`；
- 场景：static/kinematic、DF/TF、float/fixed、reset；
- 日期段和明确排除日期；
- 测站组名称及冻结后的 15 站列表；
- 输入产品规则和路径配置引用；
- GREAT 可执行程序与模板标识；
- 日任务并发数和重试策略；
- 输出要求。

日期展开规则：

- 将日期段转换为唯一、有序的 `(year, doy)` 集合；
- 正确处理闰年；
- 合并重叠日期段；
- 排除显式跳过的日期；
- 拒绝无效 DOY；
- 根据最终集合创建 N 个日任务。

## 7. 计划修订与冻结流程

```text
自然语言
→ 模型生成计划草稿或字段补丁
→ 后端合并并校验
→ 前端卡片展示
→ 用户通过卡片或聊天修改
→ 生成新修订版本
→ 完整输入预检
→ 用户确认
→ 冻结执行快照
→ 创建 N 个日任务
→ Worker 执行
→ 汇总结果
```

- 对话修改必须先显示字段差异，再由用户接受；
- 卡片修改和对话修改调用同一修订服务；
- 冻结后的计划不可原地修改；
- 参数变化通过新修订或复制实验实现；
- 任务始终引用冻结修订，保证可追溯性。

## 8. PPPFLT 专业规则

### 8.1 输入产品依赖

- DF Float：不要求 IFCB 和 UPD；
- DF Fixed：要求 UPD，不要求 IFCB；
- TF Float：要求 IFCB，不要求 UPD；
- TF Fixed：同时要求 IFCB 和 UPD。

所有场景检查：

- 15 站观测文件；
- 广播星历；
- 精密轨道与钟差；
- 偏差产品；
- 天线、潮汐、地球自转和行星星历等模型文件；
- XML 模板与 GREAT 可执行程序。

### 8.2 XML 规则

- 每个日期生成一份包含 15 站的 XML；
- 根据场景删除或保留 IFCB、UPD 节点；
- 正确设置频率、频段、静态/动态、模糊度模式和 reset；
- 输入路径、输出路径和起止时间必须与目标年份/DOY一致；
- 输出目录位于对应任务目录；
- 生成后必须通过标准 XML 解析；
- 再次读取 XML，与冻结计划做语义比对；
- 不采用字符串全局替换修改任意数字或年份。

### 8.3 现有脚本的使用原则

现有 D/F 盘脚本和配置作为专业规则与数据路径参考，不直接作为第一版无保护执行入口。只读检查已发现：

- 旧 PPPFLT 运行器的 `tool` 模块搜索路径无法从当前位置直接解析；
- 现有生成 XML 的 `filter` 标签不闭合，且已有 34 份文件不是标准 XML；
- 已生成文件的观测路径仍指向 2024 DOY 350；
- 已生成 Static DF Float XML 仍包含 IFCB 和 UPD；
- 生成器和旧运行器会各自生成不同 XML，执行链未真正接通；
- 旧运行器中 IFCB 初始化条件需要按频率类型重新核查。

因此，新适配器复用领域规则和模板含义，但以结构化 XML API 和测试重新实现配置生成与调用边界。现有科研输入和旧脚本保持只读。

## 9. 任务状态与恢复

任务状态：

- `pending`：等待执行；
- `running`：正在计算；
- `succeeded`：程序和必要输出检查通过；
- `failed`：启动、程序或输出检查失败；
- `cancelled`：用户停止；
- `interrupted`：服务、电脑或进程异常中断。

执行规则：

- 并发数属于计划参数，默认 1；
- 应用配置设置最大并发上限；
- 每个日期独立执行、独立记录和独立重试；
- 一个日期失败不覆盖其他成功结果；
- 重试创建新的 attempt 目录，不覆盖失败证据；
- 停止实验后不再领取新任务，并终止当前 GREAT 子进程；
- 服务重启后把遗留 `running` 任务标记为 `interrupted`，由用户选择重试。

默认采用严格预检：任何必需输入缺失都会阻止整个实验进入队列。用户可以修复输入，或创建新修订明确排除缺失日期。系统不得静默跳过。

## 10. 成功条件与错误类型

首版日任务成功条件：

- GREAT 正常启动并获得可记录 PID；
- 进程退出码为 0；
- 日任务日志存在；
- 预期的 15 站结果完整且非空；
- 结果清单成功写入。

错误分类：

- `plan_validation_error`；
- `preflight_error`；
- `xml_validation_error`；
- `launch_error`；
- `solver_exit_error`；
- `missing_output_error`；
- `interrupted`；
- `model_error`。

每个错误在前端显示类型、受影响日期、简短说明、日志位置和建议操作，不能只显示“运行失败”。

模型 API 故障时，用户仍可通过卡片手动建立和编辑计划；已经冻结或正在运行的任务不依赖模型。

## 11. API 边界

建议的首版 API：

```text
POST   /chat
POST   /experiments
GET    /experiments/{id}
POST   /experiments/{id}/copy
POST   /experiments/{id}/plan/revisions
POST   /experiments/{id}/plan/validate
POST   /experiments/{id}/plan/freeze
POST   /experiments/{id}/run
GET    /experiments/{id}/tasks
POST   /experiments/{id}/stop
GET    /tasks/{id}
POST   /tasks/{id}/retry
GET    /tasks/{id}/events
GET    /tasks/{id}/results
```

实时任务状态和日志使用 SSE。第一版不需要双向 WebSocket；停止、重试和编辑仍使用普通 HTTP 请求。

## 12. 安全与开源约束

- API 默认绑定 `127.0.0.1`；
- API Key 只从环境变量或未跟踪本机配置读取；
- 浏览器不接收密钥；
- 模型不能提交任意命令；
- GREAT 使用参数数组启动，不使用模型生成的 Shell 字符串；
- 输入目录只读；
- 第一版不执行移动、归档或删除科研源数据；
- 输出只能写入配置的运行根目录；
- 公开仓库不得包含真实科研数据、密钥或无权再分发的二进制程序。

未来开源接口：

- 可替换 `ModelProvider`；
- 可增加新的解算器适配器；
- 可切换运行根目录；
- 可增加认证中间件和服务器部署；
- 提供 mock solver，使没有 GREAT 的用户能运行演示。

## 13. 测试策略

### 13.1 单元测试

- 跨年、闰年、重叠和排除日期；
- 场景与 IFCB/UPD 依赖规则；
- 计划修订、差异和冻结；
- 15 站列表快照；
- XML 结构和计划语义一致性；
- 命令参数和输出路径；
- 状态转换和重试尝试编号。

### 13.2 模拟集成测试

- mock solver 产生成功、失败、超时和缺失输出；
- Worker 领取、执行、停止和恢复；
- SSE 事件与日志；
- API 与 SQLite 状态一致性；
- 模型故障时的手动计划流程。

### 13.3 真实验收

1. 2024 DOY 350、15 站、Static DF Float、reset0；
2. 核对 XML、日志、退出码和 15 站 FLT；
3. 运行当前典型跨年日期范围；
4. 验证按实际日期集合创建 N 个任务；
5. 验证失败重试、停止恢复和最终汇总；
6. 由用户进行首轮科研正确性复核。

取得真实 `.flt` 后，再定义位置误差、收敛时间、有效历元率等定量验收标准。

## 14. 第一版完成标准

- 聊天可以生成计划草稿；
- 卡片和对话都能修改计划；
- 计划可以版本化、校验和冻结；
- 任意合法日期范围可以生成 N 个日任务；
- XML 有效且语义与冻结计划一致；
- 输入缺失不会被静默跳过；
- GREAT 可以安全启动、停止和重试；
- 日任务可恢复并保留每次尝试证据；
- 网页显示实时状态、日志和结果清单；
- 所有新代码、数据库和输出位于 `F:\GREAT_Agent`；
- 不修改现有科研输入和旧脚本；
- 模拟模式可在没有 GREAT 和真实数据的环境运行。

## 15. 已接受的后续调整原则

本设计固定系统边界、安全原则、任务粒度和可追溯性要求。具体字段、页面排版、输出识别规则、并发上限和数值质量指标允许在实际开发与自测中根据真实程序行为调整，但调整不得破坏以下约束：

- 模型不直接执行任意命令；
- 计划执行前必须冻结；
- 输入数据只读；
- 每日任务可恢复；
- 输出隔离且可追溯；
- 错误不得静默吞掉；
- 日期任务数由实际计划动态产生。
